## 教程里的三种说法：先看图例

读任何一页时，先看这段写法的“身份”。三种身份保证的东西不同，判断方式也不同：

| 你看到的样子 | 它保证什么 | 你该怎么做 |
| --- | --- | --- |
| 没有标注的语法与语义 | 按规范编写，设计已经定下；不保证每个发行版都已完成 | 照教程学写法，落地前用最小片段确认 |
| 标了 `!!! note "实现状态"` | 目标设计或仍在实现的能力 | 可以学写法，但别当成已验收行为 |
| 命令与工具行为 | 以当前发行的实际输出为准；选项、缓存位置和产物命名可能随版本变 | 用 `el --help`、`el COMMAND --help` 和实际输出核对 |

三个具体例子，感受一下区别：

- **没有标注**：`Number` 是精确有理数，`1 / 3` 保留精确值。这是规范定下的语义，教程直接讲。
- **实现状态**：浏览器里的 GUI 与 `wasm32-browser` 目标还在实现与验收中。写法可以先学，但当前发行会在参数检查时明确拒绝这个目标。
- **以发行输出为准**：`el build` 没有 `--target`，跨目标要走 `--compile-native`。这是当前工具的行为，不是语言语义。

!!! warning "常见坑：把规范写法当成发行版事实"
    现象：照着教程写完，当前发行却报“未知选项”或直接拒绝某个目标。先回到上面的图例对一下身份：它可能是「实现状态」或命令行为差异，而不是你写错了。

## 三分钟自查：这个写法现在能不能用

1. **先跑最小片段。** 从一行开始，能跑再逐步加上你要用的构造：

    ```el
    console.stdout.writeLine("probe")
    ```

2. **读诊断。** 编译错误会给出文件、行号、期望元素与实际遇到的 token；运行错误看异常类型和消息。
3. **查 `el --help`。** 当前发行实际支持哪些子命令以它为准；`el COMMAND --help` 给该命令的参数说明。
4. **跑一遍测试。** `el test` 能跑项目自带的行为用例，比逐条猜可靠。

不要仅凭“文档里写了”就断定当前发行支持；同样，也不要仅凭“某个文档没写”就断定语言不支持。

## 各部分的成熟度不同

| 部分 | 教程的处理 |
| --- | --- |
| 词法、表达式、控制流、函数、类、模块 | 按规范写；这些是语言核心，教程中的例子尽量只依赖已定写法 |
| 标准库模块路径与函数 | 以 `src/stdlib` 的真实导出为准；查不到的 API 不写进示例 |
| Console 输出 | 文字走 `console.stdout.write`／`writeLine`，结构化值走等级对象的 `.value(...)` |
| 项目配置与 CLI | `el run ENTRY`、`el build ENTRY` 是最稳的入口；项目文件字段按规范介绍 |
| GUI | 按规范与 `user-interface` 源码的真实导出写；示例优先使用已核实的元素 API |
| 数据库、证明、跨目标产物 | 教程只做概念介绍，不展开未稳定的细节 |

## 为什么这里没有未完成清单

未完成项变化很快，逐条抄进教程只会制造过期信息。具体缺口、所需证据和验收规则由项目自己的状态文档维护；教程只在会影响写法的地方用「实现状态」提醒。

这也是本页只给判断方法、不列“还有什么没做”的原因：清单一旦写进正文，读者就分不清它是今天的事实、上周的事实，还是目标设计。

## 发现教程和发行对不上，怎么办

先确认两件事：

1. 发行版版本是否包含对应能力。
2. 是不是把规范里的目标写法当成了已验收行为。

确认后仍然对不上，欢迎在[教程仓库](https://github.com/steve02081504/el-doc)提 issue，附上最小复现和 `el --help` 的输出。

## 带走这三样

- 三种说法：没有标注（按规范学）、`实现状态`（先确认再用）、命令与工具行为（以发行输出为准）。
- 自查顺序：最小片段 → 读诊断 → `el --help` → `el test`。
- 这里不列未完成清单；缺口与验收规则由项目状态文档维护，教程只在影响写法处提醒。
