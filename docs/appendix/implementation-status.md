# 规范与实现边界

这份教程按 EL 的语言规范编写，而不是按某一个发行版的行为倒推。规范描述的是目标合同；发行版可能只覆盖其中一部分，也可能和教程依据的规范版本不同。读教程时把这两件事分开，能少很多困惑。

## 怎么判断一个写法现在能不能用

先写最小片段，直接运行：

```el
console.stdout.writeLine("probe")
```

如果这一行能跑，再逐步加上你要用的构造。遇到编译错误时看诊断给的文件、行号和期望元素；遇到运行错误时看异常类型和消息。`el --help` 能告诉你当前发行实际提供哪些子命令，`el test` 能跑项目自带的行为用例。

不要仅凭“文档里写了”就断定当前发行支持。同样，也不要仅凭“某个文档没写”就断定语言不支持。

## 教程里的三种说法

- **没有标注的语法与语义**：按规范编写，设计已经定下。教程负责把它讲清楚，不承诺每个发行版都已完成。
- **标了 `!!! note "实现状态"` 的内容**：目标设计或仍在实现的能力。可以学写法，但落地前先用最小片段确认。
- **命令与工具行为**：以当前发行的实际输出为准。不同版本之间，命令选项、缓存位置和产物命名可能变化。

## 各部分的成熟度不同

| 部分 | 教程的处理 |
| --- | --- |
| 词法、表达式、控制流、函数、类、模块 | 按规范写；这些是语言核心，教程中的例子尽量只依赖已定写法 |
| 标准库模块路径与函数 | 以 `src/stdlib` 的真实导出为准；查不到的 API 不写进示例 |
| Console 输出 | 文字走 `console.stdout.write`／`writeLine`，结构化值走等级对象的 `.value(...)` |
| 项目配置与 CLI | `el run ENTRY`、`el build ENTRY` 是最稳的入口；项目文件字段按规范介绍 |
| GUI | 按规范与 `user-interface` 源码的真实导出写；示例优先使用已核实的元素 API |
| 数据库、证明、跨目标产物 | 教程只做概念介绍，不展开未稳定的细节 |

## 为什么不在教程里列未完成清单

未完成项变化很快，逐条抄进教程只会制造过期信息。具体缺口、所需证据和验收规则由项目自己的状态文档维护；教程只在会影响写法的地方用「实现状态」提醒。

如果你发现教程里的例子与当前发行不符，先确认两件事：

1. 发行版版本是否包含对应能力。
2. 是不是把规范里的目标写法当成了已验收行为。

确认后仍然对不上，欢迎在[教程仓库](https://github.com/steve02081504/el-doc)提 issue，附上最小复现和 `el --help` 的输出。
