# 左值、右值与亡值

表达式既有类型，也有使用方式：有的指向一个可访问的位置，有的提供一个可交付的值。移动后，原来的来源还可能变成不能正常读取的亡值。

| 名称 | 怎么理解 | 对调用和后续使用的影响 |
| --- | --- | --- |
| 左值 | 能表示某个已有位置的访问；是否可写另行判断 | 可写左值可以借给 `ref` 参数；只读左值不能 |
| 右值 | 在该位置可作为右值消费的表达式，例如新构造的结果 | 可以匹配 `rvalue` 参数；接管还要看 `take` |
| 亡值 | 移动或接管已提交后的来源状态 | 不能正常读取或复制；必要清理和明确的残余协议仍须遵守 |

## 一个名字的最后使用可能成为右值

下面是语义片段，展示调用现场的判断，并非输出示例：

```el
let count = 3
let next = count
```

`count` 是具名绑定；如果编译器能按规范证明这里是符合条件的最后一次值读取，这次读取可以按右值处理并移动。不能证明时保持左值，按类型的普通复制或共享规则处理。这个分析受控制流、捕获和借用等条件限制，并非看到名字最后出现一次就一定移动。

`const` 与值类别是不同的问题：只读左值仍是左值，不因为不能写就变成右值。对象的类别也不由类型的 `copy` 或 `shared` 模式单独决定，见[赋值、复制与共享](assignment-semantics.md)。

## `rvalue`、`rvalue(...)` 和 `take` 有什么区别

| 写法 | 含义 |
| --- | --- |
| 参数前的 `rvalue` | 限制实参在调用处能以右值匹配；进入函数后是普通具名局部绑定，本身不接管调用者来源 |
| `rvalue(source)` | 普通函数调用，显式消费来源并交出所有权；接管提交后来源成为亡值 |
| 参数前的 `take` | 表达接管；提交后调用者的来源成为亡值 |
| 参数前的 `ref` | 借用调用者的可写槽位，参数赋值会写回该槽位 |

最后使用可以使一次读取参与右值匹配；若同一实参同时符合 `ref` 和 `rvalue`，匹配的 `ref` 更具体。类型转换和多个参数还会影响最终重载，见[重载解析](overload-resolution.md)和[函数](functions.md)。

## 亡值不是 C++ 的 xvalue

EL 用左值／右值描述访问类别，也用 live、dead 等描述生命状态。亡值（dead）是已经被消费的来源，不是 C++ 中仍可作为表达式使用的 xvalue；不要把两种语言的术语一一等同。接管后的接收方可以持有存活的右值，而原来源已经是亡值。

共享类型也遵守这个区别：移动一个共享引用会消费该来源的引用，不会因此移动或析构其他持有者仍在使用的底层对象。借用是否仍有效、对象何时清理，见[生命周期、借用与清理](lifetimes.md)。

## 常见误解

- “右值一定已经被移动”：右值描述使用类别，实际是否接管取决于所选操作。
- “有名字就永远是左值”：符合条件的最后一次读取可按右值处理。
- “亡值只是旧数据不再重要”：普通读取或复制亡值不合法；需重新构造或赋值建立新生命后才能按新值使用。
- “右值保证对象独占”：共享类型的其他持有者仍可能使用同一对象。
