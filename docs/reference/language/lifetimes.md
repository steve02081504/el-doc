# 生命周期、借用与清理

这一页回答三个常见问题：复制一个值会得到什么，引用能用到什么时候，对象何时析构。判断时要区分名称、绑定、对象和存储：名称离开作用域不一定结束对象寿命；对象析构也不等于它占用的存储立刻回收。

## 复制、共享和借用的区别

| 方式 | 得到什么 | 能否通过它改变原槽位 | 谁负责保持对象有效 |
| --- | --- | --- | --- |
| `copy` 值 | 独立对象；具体复制深度由复制构造决定 | 否 | 新对象的所有者 |
| `shared` 值 | 指向同一对象的共享引用 | 不因共享本身而写回绑定槽位 | 各个共享持有者共同维持对象可用 |
| `ref` 参数 | 对调用者可写槽位的借用 | 能；给参数赋值会写回原槽位 | 借用来源必须覆盖所有实际使用 |
| 普通值参数 | 按类型的 copy/shared 策略取得的局部绑定 | 否；重绑只改局部参数 | 参数的正常值策略和生命周期 |
| `take` | 按接管协议转移值 | 转移已提交后，原持有者不能照常再用 | 接收方成为新的持有者 |

具名用户类型必须声明 `@assign(mode: "copy")` 或 `@assign(mode: "shared")`。Number、Bool、Text 是 copy 值语义；对象字面量的匿名类型采用 shared。共享引用不自带并发写入同步。

```el
let first = 3
let second = first
```

对 copy 类型，这两个绑定保存独立值；对 shared 类型，同样的初始化会共享同一个对象。`===` 比较对象身份，所以它回答的是“是不是同一个对象”，而不是“内容是否相等”。

## 哪些复制会被省略

新构造结果或已拥有的右值直接交给同类型绑定、按值参数或返回结果时，语言要求直接交付，不额外制造中间副本。拥有临时值的隐式复制链也可以合并，因此不能依赖这些临时副本的复制次数、身份或副作用。独立具名值仍保持隔离，真实资源仍须释放。

具体例子、必要复制与自动移动的区别见[复制消除](copy-elision.md)。先分清位置与可消费值，可读[左值、右值与亡值](value-categories.md)；类型策略与引用参数的两层规则见[赋值、复制与共享](assignment-semantics.md)。

## `ref` 借用哪一块存储

`ref` 参数借用的是可写槽位，不只是某个对象的只读视图。读取参数会读取原槽，给参数赋值会写回调用者的槽位；普通值参数重绑则只影响局部绑定。多个引用可以同时指向同一槽位。

| 使用情形 | 规则 |
| --- | --- |
| 将 `ref` 传给函数 | 实参须为可写左值；类型、可写性和值类别仍要匹配 |
| 返回 `ref` 或 `rvalue` 引用 | 返回引用不会延长局部槽位寿命；来源必须本来就足够长寿 |
| 借用视图 | 视图本身不拥有底层存储，来源必须覆盖视图的每次使用 |
| 异步挂起 | 挂起不会结束活动借用；恢复后仍会用到的来源必须保持有效 |
| 容器扩容 | 逻辑位置之后可能重新定位；已经借出的物理槽位引用可能失效 |
| 删除后在同一索引插入 | 新元素不会让指向旧元素槽位的引用重新有效 |

活动借用期间，不得移动或析构其来源而使借用失效。确定悬垂属于未定义行为，ELF 对可确定的违规报错；若静态分析不能排除失效，则给出警告。类型和值类别的准入仍是编译期合同，不能拿后续的生命周期诊断代替。

## lambda 捕获绑定还是值快照

lambda 自动捕获外层逻辑绑定，而不是在创建闭包时复制一份值快照。多个闭包捕获同一绑定时，会看到同一绑定及之后的赋值；闭包逃逸时，捕获绑定必须继续有效。跨 task 共享不可变捕获可以安全读取；可能并发写入的捕获需要 Atomic 或显式异步 Mutex 等同步合同。

## 析构通常发生在什么时候

需要先看具体输出顺序，可直接读[激进生命周期与析构时机](aggressive-lifetimes.md)：同一程序采用默认策略和 `scope` 策略时，析构与后续语句的先后顺序不同。

具体类上的 `@destruct` 选择该具体类的策略，不沿继承链继承：

| 策略 | 析构时点 | 适用直觉 |
| --- | --- | --- |
| `aggressive`（默认） | 对象不再有使用者后，通常在最后一次使用处析构 | 尽早结束对象寿命 |
| `scope` | 至少等到所属名称作用域结束 | 需要把临时或绑定保留到区域末尾 |

仍有使用者时，两种策略都不能析构对象。同一析构点可析构的多个变量按声明逆序清理；若一个对象在更早位置已经没有使用者，它可以在那里先析构，不必等到后声明但仍在用的对象。共享对象只析构一次，按最后释放它的绑定确定排序位置。析构触发和存储回收是两个事件。

## 构造失败、GC 和引用环

构造失败时只清理已经成功构造的部分。正常退出须完成必要清理；清理本身可以异步或失败。GC 池中的对象没有确定的析构点，因此文件、锁等外部资源应有明确关闭方式，不能等 GC 才释放。

| GC 状态 | 强拥有引用环的规则 | 析构环内对象时的规则 |
| --- | --- | --- |
| 开启 | 环可以存在并由追踪回收处理 | 环内对象的析构顺序未定义；析构期间访问环中其他对象也属未定义行为 |
| 关闭 | 源码强拥有引用形成环本身即为未定义行为 | 不存在以确定环析构顺序为前提的保证 |

GC 关闭时，当前实现可能不回收强拥有环并因此泄漏；这只是当前实现表现，不是语言对未定义行为结果的限制。借用边或非拥有链接不自动构成强拥有环。
