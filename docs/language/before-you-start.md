# 读语言之前

## 先猜：这段程序打印什么？

```el
const a = 1
a = 2
console.stdout.write(a)
```

猜 `2`？`1`？还是什么都不输出？

??? question "先猜：上面三个答案里，哪一个对？"
    一个都不对——因为没有标准答案。规范（SYN-78）把对 `const` 槽位的重赋、复合赋值、步进和经别名写回都列为**未定义行为**。程序走到这里就没有规定的结果了：`a` 可以是任何值——`2`、`1`、上一次运行留下的东西，或者让后面某一行崩掉。语言不承诺它打印什么，也不承诺它在哪里停下。

==“我这边跑出来是 `2`”不构成证据：未定义行为的意思不是结果随机，而是语言对结果不做任何承诺。==

## 编译器不会替你兜底

`elc` 和 `el run` 把源码翻译成可执行的东西并按规范执行；它们**不保证**为未定义行为报错（SYN-78 原文：ELC 不保证报错）。所以别指望编译器先停下来替你做一遍检查：这类程序可能一路跑下去，把未定义的结果当成正常输出。

```sh
el formatter --check hazing.el
```

`elf` 是负责报错的那一侧，命令入口是 `el formatter`。它同时检查格式、`unsafe` 许可与可简化写法，并复用同一套语义分析，因此能对确定违规（例如上面那次 `const` 重赋）报错；有需要处理的内容或规则违规时以非零退出码结束，可以直接放进提交前检查或 CI。对无法判定的情况，它必须明确报告“未知”，不能假装检查过。命令、选项与退出码见[工具链](../toolchain.md)。

!!! example "动手 30 秒"
    把上面那段代码存成 `hazing.el`，先 `el run hazing.el`，再 `el formatter --check hazing.el`。第二次命令以非零退出码结束、并在报错里指出 `const` 槽位的写入，就说明你亲眼看到了“能跑但违规”。

这条标准落到日常只有一句话：别拿一次成功的运行当验收。

!!! warning "常见坑：能运行不等于正确"
    **现象。** `el run` 顺利跑完，屏幕上还有看起来合理的输出，文件里却写着 `const` 重赋。**原因。** `el run` 只保证翻译并执行，不保证为 UB 报错。**改法。** 交付前跑一次 `el formatter --check`，等它以 0 退出才算写完。

## 未定义行为长什么样

它不会在屏幕上写“我是 UB”。读者会遇到的形态大致是这些：

- 同一份文件跑两次打印不同结果，或者只在你加了打印语句之后才“正常”。
- 程序在很远的、看上去无关的行上崩掉——因为写入已经破坏了一个你以为没人动过的值。
- 换个构建选项或编译器版本就换了行为，代码一个字没改。
- 最糟的一种：结果一直合理，直到某次数据换了形态才暴露。

==判据不在输出里，在规范里：只有规范承诺了的行为才值得依赖。==

“我试过，能跑”因此不构成验证：未定义行为允许任何结果，一次运行碰巧合理什么也不保证。要问就问“规范第几章说了这个”，或者“`el formatter --check` 干净吗”。

这类“语言不承诺结果”的地方不止 `const` 写：`Number` 的默认溢出策略就是 `overflow: "ub"`（语言规范第 4 章 NUM-26），[数值与位类型](numeric-types.md)会再遇到它。

??? note "可选 · 深入：为什么 `elc` 敢不做这些检查"
    规范把那些只用于验证安全、不参与正确代码生成的分析交给 `elf`，并允许 `elc` 假定它们已经通过、不重复验证（语言规范第 11 章 CLI-5.6）。于是同一个文件在 `elc` 眼里可能是良构的，在 `elf` 眼里却是确定违规。这不是实现偷懒，是分工——所以检查命令要单独跑。

## 带走这三样

- 未定义行为不是“结果随机”，而是“语言不承诺任何结果”，包括崩溃位置。
- `elc`／`el run` 不为 UB 兜底，确定违规由 `el formatter --check` 报告。
- 判断代码对不对，看检查命令的退出码，不看上一次运行碰巧打印了什么。
